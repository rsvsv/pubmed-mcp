## 第 4 批：大量导出提速，防超时

**问题。** export 超过 9999 条时按发表日期二分切片，空区间也要探一次，每页固定 1000 条串行取。例如 10,186 条用了 67 次请求、43 秒〔未核实，来源：子代理〕。2 万条以上有超时风险〔未核实，来源：子代理〕。

**方案。**
1. **整窗剥离。** esearch 加 `sort=pub_date`（降序）、`retmax=9999`，一次拿一个整窗。取最后一条的发表日期作为下一窗的 `maxdate`，再把边界日当天单独补查、去重。预计请求数降到约 5 次〔推算，来源：子代理；不能证明边界日不漏，正确性另见第 3 点〕。
2. **挂可选参数** `fast=True`，默认路径不变。理由：剥离法会改变 PMID 顺序和片数，违反「默认输出不变」。
3. **兜底核对。** 这个方法依赖一个前提：每条记录的 sortpubdate 不早于它能被 `[dp]` 命中的所有日期。这一点的普遍性⚠️【待确认】。保留现有的「取回数 ≠ 命中数」警告，并在不一致时自动退回切片法。
4. **超时。** MCP progress 通知能否重置客户端超时⚠️【待确认】。在核实之前，不对外承诺「不会超时」，只在文档中给出分段导出的写法。

**验收。** 三个检索式（约 1 万、约 3 万、约 9 万条）分别用 fast 和默认切片法跑，PMID 集合须完全一致；记录请求数和耗时。

**规模。** 约 110 行，加测试〔推算〕。描述约增加 20 字〔推算〕。

## 第 5 批：追引用（滚雪球）

**问题。**
- `links(to=citedin)` 最多展示 200 个号，多号批量时每号 50 个；`to=pubmed` 写死只展示 8 个。
- 只返回裸 PMID，没有标题。
- 没有 as_json。
- 不能拿 PMID 清单直接导出，也不能和上次的导出结果求差集。

**已知事实。** elink 一次请求就返回全部 citedin。实测 26017442 一次拿到 11,934 条〔实测 2026-11-12，主会话〕。因此翻页只需在本地切片，不增加请求。

**方案。**
1. **links 增加可选参数：**
   - `offset` / `limit`：本地分页。
   - `as_json`：返回去重后的号、每个源 PMID 的计数，以及跨源合并后的唯一号。
   - `out_path`：全量落盘。
2. **PMID 清单输入。** export 和 fetch 增加 `pmids=` 或 `pmids_path=`。必须用 POST 传号，GET 拼 `[uid] OR` 约 200 个号就会撞 414〔未核实，来源：子代理〕；POST 能否传 1 万个号⚠️【待确认】，需实测。
3. **集合运算。** diff 增加 `baseline_path`，用于把新检索与上次的导出文件对比。纯本地计算，不发请求。
4. **snowball 一步工具（放最后做）：** 种子 PMID → 正向 citedin 加反向 refs → 去重 → 扣除已有集合 → 落盘候选清单（带标题）。必须自带 out_path，否则上万候选交付不出来。

**前置条件。** 描述预算不够。需要先压缩 search（838 字）、count、mesh 的描述，或把上限放宽到约 3000。这个决定需要用户拍板。

**规模。** 约 350 行〔推算〕。

## 第 6 批：PRISMA 留痕与更新检索

**问题。**
- 不能按入库日期（edat）检索。做更新检索时，会漏掉「新入库但发表年份较早」的文献。
- 导出文件里没有记录检索式和执行时间。
- 留痕功能默认关闭，开启后也没有汇总成 PRISMA 检索表的入口。

**方案。**
1. **日期类型参数。** search、count、export 增加 `datetype="pdat"|"edat"`，默认 pdat，输出不变。
2. **侧车文件。** export 在导出文件旁写 `<文件>.meta.json`，内容包括：检索式、NCBI 执行式、起止时间、起始和结束命中数、切片明细、sha256、工具版本。这会改变导出目录里的文件清单，`tests/test_exercise_fixes.py` 的目录断言需同步修改。
3. **汇总命令。** 新增命令行 `pubmed-mcp --audit-report <留痕文件>`，输出 PRISMA-S 风格的检索记录表（Markdown 或 CSV）。走命令行，不占工具描述预算。
4. **留痕提示。** 未开启留痕时，export 结果末尾加一行提示，告诉用户怎样开启。

**规模。** 约 300 行〔推算〕。
