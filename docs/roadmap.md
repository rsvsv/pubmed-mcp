## 第 6 批：先形成可追溯的检索记录〔本项目自订批次〕

### 交付 A：审计记录与离线报告

工作区已实现，尚未发布：见 [使用说明](audit-report.md)。下文保留设计契约；报告只整理日志，不验证关联导出文件，文件核验归入交付 B。

拟定入口：`pubmed-mcp --audit-report <searches.jsonl> --out <report.md或report.csv>`。这是 CLI，不增加 MCP 工具。扩展 `main` 的参数分派时保留已有命令，未知参数必须报错。

先给新记录增加 `audit_schema`、`run_id`、独立唯一的 `event_id`、带时区的 `started_at` / `finished_at`、工具版本、输入参数与实际执行参数。同一编排运行共享 `run_id`，每次事件使用不同 `event_id`；不能按 `run_id` 去重整次运行。旧事件没有标识时保留每个输入位置，不用查询文本猜测去重。export 记录须包含完整执行式、文件格式与路径、哈希、检回/实际写入数、完整缺失名单、核对状态和警告。结束时间在题录抓取及文件发布完成后采集；已有 `ended` 字段若继续表示取号结束，须保留原含义并注明。

报告只整理已存在的证据：数据库、访问平台、检索时间、原始式与执行式、限制条件、计数、导出文件和警告。每次事件单列，不能把反复试检的命中数相加当筛选样本量。旧记录没有的字段写 `⚠️【待确认】`，不得补造时区、起止时间或完整执行式。

失败契约：

- CLI 接受重复的输入路径参数；相同物理输入文件只读一次。新事件按 `event_id` 去重，若相同标识内容冲突则报错并给出来源位置，不能任取一条。旧记录按文件哈希与行号定位，同一查询的不同执行保留。
- 报告解析到损坏 JSONL 行时，默认报行号并停止，不产生正式报告；可显式 `--skip-invalid` 输出部分报告，但报告必须列出跳过行号、原因和“输入不完整”。
- 输出文件已存在、与输入同路径或指向同一文件时，在写入前拒绝；采用独立临时文件和不覆盖发布。
- 新审计写入使用锁保护同进程追加；多进程并发改为独立日志文件，不承诺共享文件无交错。报告入口可接受多个明确路径，按事件标识去重，并保留来源文件/行号。
- 审计失败不使已成功检索作废。`_audit` 返回 `disabled` / `written` / `failed` 与脱敏错误；有 JSON 模式的工具新增 `audit_status`，失败时所有工具的文本返回增加警告，stderr 同时保留。关闭或成功时默认文本不变。不得把“配置已开启”当成“日志已写入”。
- 不写 API key、email 或原始请求 URL。查询本身可能包含研究主题，审计仍由用户显式开启。

验收：旧日志兼容、缺字段、损坏行、重复事件、并发写入、权限错误、输出冲突；报告数字逐条能回到来源事件，不能凭报告推断纳入数。通过报告测试前核对 PRISMA-S 原始条目；原文逐字核验目前为 `⚠️【待确认】`，报告先命名“检索记录表”。

### 交付 B：导出伴随元数据

拟定参数：`export(..., metadata=False)`；显式开启后，文件旁写 `<path>.meta.json`。默认不增加文件。伴随元数据与审计共用记录构造器，避免两套数字口径。

预先检查主文件和伴随路径，任何已有文件都不覆盖；所有检查仍须配合原子发布防止并发竞争。先写完数据临时文件并计算哈希，再发布数据，随后以已发布数据的完成时间构造、写入并发布元数据。最终元数据发布状态写进返回值与审计，不预先在元数据自身宣称发布成功。不声称两个独立文件能原子提交。

主文件失败时清理本次临时文件，不发布元数据。主文件成功但元数据失败时保留主文件，明确返回 `metadata_status=failed`、数据路径与错误；不能只抛笼统错误使用户误以为没有导出。返回状态另含 `not_requested` / `written`，成功时给出元数据路径。进程中断可能留下主文件而无元数据；显式验证入口报告缺元数据，不自动猜配。孤立临时文件只清理由本次运行拥有的路径。

元数据包含 `schema`、`run_id`、本次导出的唯一 `event_id`、数据哈希和实际完成时间。拟定离线入口：`pubmed-mcp --verify-export <data-path> [--meta <meta-path>]`；未给 meta 时只检查约定的同名伴随路径，不搜索猜配。返回 `verified` / `missing_data` / `missing_meta` / `invalid_meta` / `hash_mismatch`，这里 verified 只证明文件与元数据哈希绑定，不证明检索完整。

目录移动后通过显式数据路径重新验证，不依赖旧绝对路径继续有效。审计报告只对事件里明确记录的文件尝试验证，并标注文件是否在当前机器可访问；发布后、审计前中断的孤立文件不会被报告自动发现，必须用 `--verify-export` 指定路径。没有元数据就报 `missing_meta`，不补造一次成功审计。

验收：主文件失败、元数据写入/发布失败、并发抢占任一路径、取消及中断后的可识别状态；默认文件列表不变；审计、JSON、元数据字段一致。新增输出路径和状态必须走真实 SDK 包装层测试。

### 交付 C：统一日期参数与补检流程

拟定接口：search/count 增加 `datetype="pdat"|"edat"`；export 增加相同日期类型及 `mindate` / `maxdate` / `reldate`，默认无日期限制且类型为 pdat。传入不支持的类型在联网前拒绝。

日期实现必须区分“用户限定”与“内部拆片”：

- 用户 term 内的日期表达式不改写；与参数日期组合时由 NCBI 做 AND，输出分别说明字段与有效区间。
- search/count 的相对天数继续交给 NCBI 解释，不能改成本机日历换算。日期提示和空交集判断不得把 edat 与 pdat 当成同一字段。
- export 在开始时将有效用户条件固定为整个运行共用的查询范围，再额外应用内部切片条件。不能把下一片的日期覆盖到用户限定上。
- reldate 的固定绝对区间必须有可核对的 NCBI 回显；无法取得时，export 拒绝本次相对日期导出并提示改用显式区间。不能在跨日导出中让每次请求重新解释相对日期。
- edat 大结果集的拆片语义须专项验证。未通过之前，窗口内日期检索可以单独交付，显式选择 edat 的超窗导出在发布文件前拒绝并说明限制；不自动换成 pdat。现有 term 内 `[edat]` 配默认 pdat 拆片的行为保持原契约，不能据此宣称新的 edat 拆片已验证。

推荐补检流程：记录上次实际检索范围；新一轮按入库日期设重叠区间；对旧 PMID 集合求新增。重叠长度由项目方案明确，本文不设未经验证的默认天数。edat 不覆盖所有旧记录的后续内容修改，因此补检不能承诺发现所有新符合条件的旧记录；必要时完整重跑并比较集合。

验收：新入库旧发表年、term 内双日期字段、相对日期跨日、单端日期补全、日期冲突、旧默认调用一致；从参数到所有分页/切片的调用捕获必须一致。联网记录执行式和 PMID 集合差，不能只对命中数。

## 第 5 批：让追引用结果接入筛选〔本项目自订批次〕

### 交付 A：links 完整结果与来源关系

拟定参数：`links(..., as_json=False, out_path="", offset=0, limit=None)`〔本项目自订默认参数；未传新参数保留旧展示上限〕。

内部先得到带来源的完整结果模型，再分别渲染旧文本、JSON、文件。保留每个源 PMID 的 `source_status`、`relation`、目标 ID 列表及错误；另给跨源唯一候选。不能为了去重丢掉“哪个种子、哪个方向找到这篇”的边关系。

全量 JSON 使用带版本标识的 `schema`，PubMed 候选集中存于 `candidate_pmids`，来源边另存 `edges`；混合或非 PubMed 目标不得填入该候选字段。后续清单 CLI 明确识别此格式，不从任意 JSON 递归提取数字。

分页只控制返回给对话的列表，offset/limit 按每个源的去重目标列表切片；counts 在切片前计算，响应明示 per-source 口径。每次调用仍可能重新请求 NCBI，不宣称多次分页共享快照。`out_path` 写本次全量来源关系和目标集合，不受展示分页影响，返回文件摘要而非同时回传全量正文。首版采用 JSON 文件，不新增多种文件格式。

引用方向使用 refs/citedin，保留 PubMed 关系覆盖有限的提示；基因等其他数据库目标不能作为 PMID 候选。存在性未知与无关联分开；部分源失败仍交付成功源并列出失败源，全部失败报错。任何输入/输出上限需显式检查和告警，不在文件中静默截断。

验收：展示与文件完整性、多源重复、同一目标多条来源边、某源/全部源失败、空关系与未知源、不同数据库 ID、分页越界、目标路径竞争。以抓包夹具核对关系归属，并做小规模联网方向抽查。

### 交付 B：直接从 PMID 文件导出

拟定 CLI：`pubmed-mcp --export-pmids <ids.txt> --out <path> --format <format>`。复用现有格式 writer 和核对字段，不先把 PMID 拼成检索式再检索。首版不修改 export 的必填 term，也不向 fetch_abstracts 重复增加其已有的 `pmids` 参数。

输入接受纯 PMID 文本或本项目带已支持 `schema` 的候选 JSON。文本逐行读取、归一化、保序去重；候选 JSON 只读取明确的 `candidate_pmids` 并验证全部 ID，保留来源文件绑定。未知 schema、歧义数字、非法行报源行号或字段位置，不悄悄提取数字。记录输入文件哈希、原始数、唯一数、实际写入数及缺失名单。源文件和输出同路径/同文件须拒绝；超出已有安全上限则明确报错并提供分批建议。

不把“必须 POST”写成前提：优先复用已验证的分批 GET，按实际编码后请求长度和端点限制决定是否增加 POST。新 POST 路径须复用脱敏、限速、重试、取消和响应归属验证，不能单独绕开传输保护。

验收：空文件、BOM、空行、前导零、重复号、逗号歧义、非法 token、上限、文件冲突；输出集合与输入唯一集合核对，题录缺失完整列明；对 RIS/MEDLINE 在实际使用的文献管理软件中完成一次导入，按原字段核对作者、摘要、文章号与缺失条目。

### 交付 C：离线集合运算

拟定 CLI：`pubmed-mcp --diff-files <baseline.txt> <current.txt> --out <diff.json>`。旧在线 `diff(term_a, term_b)` 不改。

两份已有文件复用清单解析器，支持纯 PMID 文本及已知 schema 的候选 JSON；解析、归一化和集合运算全程离线。新增按 current 首次出现顺序，丢失/共同按 baseline 顺序，输出完整列表、计数、输入哈希及告警；差集文件以 `candidate_pmids` 保存新增集合，并用独立字段保存丢失与共同集合，可直接交给清单导出。输出不得覆盖输入或已有文件。需要大候选表时仍保存文件，只在对话显示摘要。

“新查询与旧文件比较”需先联网导出新集合，再调用本 CLI；报告区分查询条件变化和数据库时间变化，不能归因于某一因素。验收覆盖输入重复、不同分隔、空集合、顺序稳定、输出冲突；用独立预期集合核对，并在测试中阻断网络。

### 交付 D：单轮滚雪球编排

前述入口稳定后再提供 CLI 编排：`--snowball <seeds.txt> --baseline <existing.txt> --out <candidates.json>`。首版固定只追种子的一轮，不递归扩大范围；MCP 独立工具留到真实工作流验证之后决定。

顺序：读取种子 → 获取 refs/citedin → 按 PMID 去重 → 扣除种子和已有集合 → 抓候选标题 → 输出候选与所有来源边。输出同样带 `schema`、`candidate_pmids`、`edges`，标题单独按 PMID 关联，可直接进入清单导出。标题缺失仍保留 PMID；源请求失败、元数据失败分别报告。扣除集合只影响候选，不删除审计中取得的原始来源关系。

种子和 baseline 均复用清单解析器：文本取唯一 PMID，已知候选 JSON 只取 `candidate_pmids`。特别是差集 JSON 的该字段只代表新增集合，不能将其当完整旧检索集合；若 schema 属于差集且用作 baseline，默认拒绝并提示使用完整导出清单，避免扣除不全。

首版把复算材料一并保存到最终 JSON：归一化种子、完整 baseline 集合及其输入哈希、每个种子每个方向的原始目标名单/请求状态/错误、扣除前唯一集合、被扣除项及原因、最终候选和全部来源边。这样文件独立可复算，无需另找临时文件；在允许的安全上限内不截断，超限时报错且不发布貌似完整的结果。抓取时间按来源事件保存；标题不参与集合运算。

验收：循环引用、自引、跨种子重复、两方向同一候选、baseline 扣除、标题缺失及源请求失败；从上述保存字段离线重算必须得到同一候选集合。只生成待筛候选，不自动判断纳入。

## 第 4 批：先测量，再改大导出〔本项目自订批次〕

### 交付 A：仓内基准与正确性夹具

先将必要的可复跑基准收进仓库，脱敏后保存请求参数、返回集合、重试与分阶段耗时。分别记录取号、题录抓取、格式化、写盘及总耗时；区分格式和有无 key 的档位，不存 key。工作集覆盖窗口内、刚超窗、多片、大摘要和缺失题录，具体规模由实测选择，不引用旧方案的未核实性能数。

合成夹具必须含：同日超窗、多发表日期、边界日、缺失日期、同计数但集合替换、分页重复/跳号和运行中增删。独立真值集合来自夹具本身；旧算法只作对照，不作唯一正确性裁判。线上无法获得独立真值时，明确写比较局限。

### 交付 B：降低重复工作与内存占用

优先尝试复用切片计数、减少重复探测、按批写临时文件和有界并发。现有全局限速及重试计数保持一致；按确定顺序写入，校验 PMID 归属及跨批重复，不让网络完成顺序决定文件顺序。

流式写入仍使用独立临时文件，只有抓取和校验完成后才不覆盖发布；失败时不把残缺临时文件冒充最终结果。验收分别量取号与题录导出性能，必须保留格式内容、缺失名单和哈希验证；内存下降和性能改善只有实测后才能写入发布说明。

### 交付 C：整窗剥离只作为实验候选

不先承诺公开 `fast=True`。验证内部较大 retmax 路径时必须绕过现有公共 search 的自订夹值而不改变其默认契约；同时确认 NCBI 实际允许的取窗边界。

`sort=pub_date` 的排序日期与 `[dp]` 匹配日期的关系、同日超窗、无日期记录、记录多日期以及数据库漂移均为必须验证的前提。当前排序日期普遍关系为 `⚠️【待确认】`。仅补查末条记录的边界日不能代替该前提的验证。

对可静态验证的夹具要求完整集合一致；在线对照逐项解释差集，不能用计数相等通过验收。前提或反例验证未通过则不发布此路径，继续使用现有算法并标明局限。即使回退旧算法也不宣称得到数据库快照或总体完整性保证。

### 交付 D：可续跑题录抓取

先仅支持“已完成并持久化 PMID 清单”的题录阶段续跑；取号阶段中断重新开始，不拼接不同时点的半份搜索结果。

拟定入口扩展清单 CLI：`--export-pmids <ids-file> --out <path> --format <format> --checkpoint-dir <jobdir>`；恢复使用 `--resume-export <jobdir>`，不再接受覆盖原输入/格式的参数。查询导出先产出完整 PMID 清单，再进入这个路径，首版不为 MCP export 增加恢复状态机。

新建作业目录必须尚不存在。manifest 保存 schema、输入集合及哈希、来源查询信息（没有则明确缺失）、目标路径、格式、工具/格式化器版本、固定有序批次清单。每批记录 `batch_id`、准确 PMID 列表、批文件相对路径、哈希、抓取时间和完成状态；批号按固定清单顺序分配，批大小由各端点已验证的限制选择并持久化。恢复不随新版本默认批大小重新划分。

CSV 批文件保存无表头数据行，最终只写一次表头；RIS 保存完整记录块，MEDLINE 保存已校验的完整题录块。均按固定 PMID 清单重排、跨批验证归属并去重，使用与非续跑路径相同的编码/分隔规则；pmids 直接按固定清单写出。批文件先写临时文件再发布，之后原子更新 manifest；出现未登记批文件时重新校验或重抓，不直接认定已完成。

恢复时重新校验输入与批文件，发现损坏只重抓受影响批次；manifest 中的相对路径必须限制在作业目录，拒绝越界。参数、格式或无法兼容的版本变化则拒绝恢复，不静默混用。缺少完整 PMID 清单及其有效哈希的作业不能恢复，明确要求重新检索并使用新目录。

固定 PMID 清单不冻结题录内容，恢复可能取得更新后的元数据；记录各批抓取时间并说明这一限制。结果发布后保留作业清单供核对，清理须显式操作；继续保持不覆盖最终文件。

进度通知只用于反馈阶段、已完成批次与重试状态，不能据此承诺延长客户端超时。目标客户端的超时/取消行为为 `⚠️【待确认】`，需用实际客户端验收。

## 提交与验收边界

| 可独立交付单元 | 依赖 | 完成标准 |
|---|---|---|
| 审计结构与报告 CLI | 可靠性补丁基线 | 旧日志兼容、逐条可追溯、损坏输入不冒充完整报告 |
| 可选伴随元数据 | 统一记录构造器 | 主文件/元数据分别失败均可识别、哈希可验证 |
| 日期接口与补检流程 | 日期语义测试 | 参数、分页、切片一致；未验证超窗能力明确拒绝 |
| links 完整输出 | 来源关系模型 | 全量文件不截断、部分失败可定位 |
| PMID 文件导出与离线差集 | 已有 writer 与核对字段 | 输入输出集合可核对；差集全程断网通过 |
| 单轮滚雪球 | links、清单导出、差集 | 来源边完整、候选可重算、不自动纳入 |
| 导出基准及逐项优化 | 固定夹具和格式回归 | 正确性先通过，再报告实测收益 |
| 检查点恢复 | 固定 PMID 清单与分批 writer | 失败可恢复、损坏可检测、时间差异可追溯 |

每个单元带同一批代码的测试与文档，不把本计划视为一次性实现或发布授权。跨环境沿用现有 CI 矩阵，并覆盖实际 SDK 包装层；联网契约检查单独手动运行，不让网络波动成为日常离线回归失败。发布前完成所使用客户端和文献管理软件的真实工作流验证，未执行的明确列为限制。

## 继续延期

MeSH 精简输出、CSV 全作者字段及其他搜索元数据扩展另行排期；不因这些便利项阻塞上述闭环。其他 linkname 的语义在来源核查前不补猜测性解释。没有完整性证据的“防超时”“保证取全”“自动生成完整 PRISMA”均不作为发布承诺。
